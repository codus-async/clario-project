# Clario — Consolidated Acceptance Criteria Test Specification (`acceptance-criteria.md`)

**Document Status:** Stage 4 — Master Acceptance Criteria Test Specification (Standalone Document)

**Target Release:** Clario MVP (P0 Scope Only)

**Platform:** Responsive Web Application (All Actors)

**Launch Jurisdiction & Currency:** Nigeria (`NGN`)

## 1. Purpose and Scope

This document provides the definitive, testable Acceptance Criteria (`AC-F01-01` through `AC-F83-03`) covering positive, validation, permission, boundary, data-integrity, and exception scenarios for all 75 P0 features of Clario. QA engineers must use these criteria as objective pass/fail release gates.

---

## 2. Master Acceptance Criteria Catalogue

### Module A: Platform Administration (`F-01`–`F-05`, `F-08`)

* **AC-F01-01 (Positive — Tenant Creation):** Given an authenticated Platform Admin, When they submit the "Create Institution" form with unique Institution Name, unique Code, Timezone `Africa/Lagos`, and valid Primary Contact Email, Then the system creates the isolated tenant record, logs an audit entry (`F-82`), and dispatches an invitation email to the initial Institutional Admin (`F-71`).
* **AC-F01-02 (Validation — Duplicate Code):** Given an existing institution with code `UNILAG`, When a Platform Admin attempts to create another institution with code `unilag`, Then the system rejects the submission with a duplicate code validation error (`BR-01`).
* **AC-F01-03 (Positive — Tenant Suspension):** Given an `Active` institution, When a Platform Admin suspends the institution and provides a valid reason, Then the institution status changes to `Suspended`, an audit record with previous and new status is created (`F-82`), and subsequent academic operations by users of that institution are blocked (`F-65`, `F-66`).
* **AC-F01-04 (Permission — Unauthorized Actor):** Given an authenticated Institutional Admin or Project Coordinator, When they attempt to access the Platform Admin institution creation or suspension operations, Then the system denies access with a `403 Forbidden` error (`SEC-10`).
* **AC-F02-01 (Positive — Plan Creation):** Given an authenticated Platform Admin, When they create a plan with Price `NGN 2,500,000.00`, Billing Interval `Annual`, and Max Users `5000`, Then the plan is stored in exact integer minor units (`250000000` kobo), marked `Active`, and logged in `F-82`.
* **AC-F02-02 (Data Integrity — Archiving Plan in Use):** Given an `Active` subscription plan assigned to an institution, When a Platform Admin archives the plan, Then the plan is no longer selectable for new subscriptions, but the existing institution's active subscription remains unaffected (`DAT-01`).
* **AC-F03-01 (Positive — Institutional Billing Update & Plan Selection):** Given an authenticated Institutional Admin, When they update their institution's Billing Legal Name and Billing Email and select an `Active` plan to renew, Then the billing profile is saved, a `Pending` payment transaction is created in `NGN`, and the payment initiation workflow (`F-67`) starts.
* **AC-F03-02 (Validation — Plan Capacity Below Active Users):** Given an institution with $1,200$ active users, When an Institutional Admin attempts to select a subscription plan with a Max User Capacity of $1,000$, Then the system blocks plan selection and displays a capacity validation error (`SCA-02`).
* **AC-F03-03 (Permission — Cross-Tenant Billing Isolation):** Given an Institutional Admin of Institution A, When they attempt to view or access the billing records of Institution B, Then the system denies access with `403 Forbidden` (`BR-01`, `BR-02`).
* **AC-F04-01 (Positive — Grace Period Calculation):** Given an institution with an active subscription expiring on `2026-11-30 23:59:59 WAT` and a configured grace period of `14` days, When the subscription end timestamp passes without renewal, Then the subscription transitions to `Grace Period` with `Grace Period End Timestamp` set to `2026-12-14 23:59:59 WAT` (`SYS-07`).
* **AC-F04-02 (Validation — Invalid Grace Period Value):** Given an authenticated Platform Admin, When they attempt to set a negative grace period (`-5` days) or non-integer value, Then the system rejects the input with a validation error.
* **AC-F05-01 (Positive — Platform Admin Invitation & MFA Enforcement):** Given an authenticated Platform Admin, When they invite a new Platform Admin via email and the invitee sets a password, Then the system requires the invitee to complete MFA enrollment (`SEC-06`) before granting access to the Platform Admin console.
* **AC-F05-02 (Boundary — Prevent Self-Deactivation / Last Admin Lockout):** Given an authenticated Platform Admin, When they attempt to deactivate their own account, Then the system blocks the action and displays an error message stating that administrators cannot deactivate their own account (`DAT-01`).
* **AC-F08-01 (Permission — Block Default Academic Document & Grade Access):** Given an authenticated Platform Admin, When they attempt to access a student's project workspace, download a project document (`F-77`), or view an examiner's grading sheet, Then the system denies the request with a `403 Forbidden` response and logs the denied attempt (`BR-25`, `SEC-15`).
* **AC-F08-02 (Audit — Restricted Support Action Logging):** Given an authenticated Platform Admin executing an authorised institutional archive export (`FR-006`), When they submit the action with a valid Institutional Request Reference, Then the system records an immutable audit log entry (`F-82`) visible to the Institution's Institutional Admin (`SEC-16`, `NFR-AUD`).

### Module B: Institutional Administration (`F-09`–`F-16`, `F-18`)

* **AC-F09-01 (Positive — Faculty Creation):** Given an authenticated Institutional Admin of Institution A, When they create a Faculty named `Faculty of Engineering` with code `ENG`, Then the Faculty is saved under Institution A and logged in `F-82` (`BR-01`).
* **AC-F09-02 (Multi-Tenant Uniqueness):** Given `Faculty of Engineering` (`ENG`) exists in Institution A, When an Institutional Admin of Institution B creates `Faculty of Engineering` (`ENG`), Then the system allows it without conflict; When Institution A attempts to create a second Faculty with code `ENG`, the system rejects it with a duplicate error (`BR-01`).
* **AC-F09-03 (Data Integrity — Prevent Archiving Faculty with Active Departments):** Given a Faculty with at least one `Active` Department (`F-10`), When the Institutional Admin attempts to archive the Faculty, Then the system blocks the action and instructs the user to archive or reassign the child departments first (`DAT-01`).
* **AC-F10-01 (Positive — Department Creation):** Given an `Active` Faculty `ENG` in Institution A, When the Institutional Admin creates Department `Computer Engineering` with code `CPE` under `ENG`, Then the Department is created, linked to `ENG`, and logged in `F-82` (`BR-01`).
* **AC-F10-02 (Validation — Archived Parent Faculty):** Given an `Archived` Faculty, When an Institutional Admin attempts to create a new Department under that Faculty, Then the system rejects the action with a validation error.
* **AC-F11-01 (Positive — Programme Creation):** Given an `Active` Department `CPE`, When the Institutional Admin creates Programme `B.Eng. Computer Engineering` with code `BENG-CPE`, Then the Programme is saved under `CPE` and logged in `F-82` (`BR-01`, `BR-03`).
* **AC-F11-02 (Data Integrity — Prevent Archiving Programme with Active Session Projects):** Given a Programme with registered students in an `Active` Academic Session, When the Institutional Admin attempts to archive the Programme, Then the system blocks the action and displays an error message (`DAT-01`).
* **AC-F12-01 (Positive — Session Creation):** Given an authenticated Institutional Admin, When they create session `2026/2027` with Start Date `2026-10-01`, End Date `2027-07-31`, and Status `Active`, Then the session is created and available for Coordinator appointment (`F-15`, `BR-03`).
* **AC-F12-02 (Validation — Invalid Date Range):** Given an authenticated Institutional Admin, When they attempt to create or update a session where `End Date <= Start Date`, Then the system rejects the submission with a date validation error (`BR-NEW-01`).
* **AC-F12-03 (Data Integrity — Closed Session Read-Only Enforcement):** Given an Academic Session transitioned to `Closed`, When a Student or Examiner attempts to make a new submission or modify an assessment in that session, Then the system blocks the write operation (`DAT-01`, `DAT-02`).
* **AC-F13-01 (Positive — Single & Bulk User Registration):** Given an authenticated Institutional Admin within subscription capacity, When they create a user or upload a valid CSV of users, Then the system creates the user records scoped to the institution, dispatches activation emails (`F-71`), and records an audit log (`F-82`) (`BR-01`, `SCA-02`).
* **AC-F13-02 (Positive — User Deactivation & Session Revocation):** Given an `Active` user with an open session in the institution, When the Institutional Admin deactivates the user, Then the user's status becomes `Deactivated`, their active session is immediately invalidated (`F-65`), and their historical project/academic records remain intact (`DAT-01`, `DAT-02`).
* **AC-F13-03 (Boundary — Subscription / 5,000 User Limit Enforcement):** Given an institution at its maximum subscribed user capacity (or $5,000$ users), When the Institutional Admin attempts to create or import additional users, Then the system rejects the operation with a capacity limit error (`SCA-02`).
* **AC-F14-01 (Positive — Staff Multi-Role Assignment):** Given an academic staff user in Institution A, When the Institutional Admin assigns both `Project Supervisor` and `Project Examiner` roles to that user, Then both roles are granted and the user can switch between or access both workspaces for their respective assigned projects (`BR-16`).
* **AC-F14-02 (Validation — Student Role Mutually Exclusive with Staff/Admin Roles):** Given a user assigned the `Student` role, When an Institutional Admin attempts to assign `Project Examiner` or `Project Coordinator` to that user, Then the system rejects the assignment with a role-incompatibility error (`BR-16`).
* **AC-F14-03 (Security — Mandatory MFA Trigger on Coordinator/Admin Role):** Given a Supervisor user who has not previously enabled MFA, When the Institutional Admin assigns the `Project Coordinator` role to that user, Then the system requires the user to complete MFA setup (`SEC-06`) before accessing Coordinator features.
* **AC-F15-01 (Positive — Coordinator Scoped Appointment):** Given an `Active` staff user Dr. Adewale, Programme `B.Sc. Computer Science`, and Session `2026/2027`, When the Institutional Admin appoints Dr. Adewale as Coordinator for that Programme and Session, Then Dr. Adewale gains Coordinator access strictly for `B.Sc. Computer Science` in `2026/2027` (`BR-03`), and an audit record is created (`F-82`).
* **AC-F15-02 (Permission — Cross-Programme & Cross-Session Scope Restriction):** Given Dr. Adewale is appointed Coordinator only for `B.Sc. Computer Science` in `2026/2027`, When Dr. Adewale attempts to register students or configure milestones for `B.Sc. Software Engineering` or for Session `2025/2026`, Then the system denies access with `403 Forbidden` (`BR-02`, `BR-03`).
* **AC-F16-01 (Positive — Supervisor Record Creation):** Given an `Active` staff user in Department `CSC`, When the Institutional Admin creates a Supervisor Record with Title `Dr.`, Department `CSC`, and Status `Available`, Then the user is granted the `Project Supervisor` role (`F-14`) and appears as an eligible Supervisor for `CSC` programmes in `F-24` (`BR-01`).
* **AC-F16-02 (Workflow — Unavailable Supervisor Blocked from New Assignments):** Given a Supervisor whose Eligibility Status is changed to `Unavailable / On Leave` by the Institutional Admin, When a Project Coordinator attempts to assign a new student or group to that Supervisor in `F-24`, Then the Supervisor is excluded/blocked from new assignment selection.
* **AC-F18-01 (Permission — Block Document Download by Institutional Admin):** Given an authenticated Institutional Admin of Institution A, When they attempt to retrieve or download a project document uploaded by a student in Institution A (`F-77`), Then the system denies the request with a `403 Forbidden` error (`BR-25`, `SEC-14`).
* **AC-F18-02 (Permission — Block Academic Feedback & Grade Visibility):** Given an authenticated Institutional Admin of Institution A, When they attempt to access a project's submission feedback thread (`F-34`) or assessment breakdown (`F-58`, `F-61`), Then the system denies access and does not expose any academic feedback or grade data (`BR-25`).

### Module C: Project Registration, Topics and Allocation (`F-19`–`F-24`)

* **AC-F19-01 (Positive — Cohort Registration):** Given an authenticated Project Coordinator appointed to `B.Sc. Computer Science` for `2026/2027`, When they register a student with Matriculation Number `CSC/2022/045` into the cohort, Then the student record is created with status `Registered`, the student can access their workspace (`F-28`), and a notification is sent (`BR-03`).
* **AC-F19-02 (Validation — Duplicate Student in Cohort):** Given student `CSC/2022/045` is already registered in `B.Sc. Computer Science` (`2026/2027`), When the Coordinator attempts to register the same student again in the same Programme and Session, Then the system rejects the duplicate registration with a validation error (`BR-03`).
* **AC-F19-03 (Permission — Out-of-Scope Programme):** Given a Coordinator appointed only to `B.Sc. Computer Science`, When they attempt to register a student into `B.Sc. Information Systems`, Then the system denies the action with a `403 Forbidden` error (`BR-03`).
* **AC-F20-01 (Positive — Student Proposal Before Supervisor Assignment):** Given a registered Student in an active Programme and Session who does not yet have an assigned Supervisor, When the Student submits a valid topic proposal, Then the system records the proposal with status `Submitted - Awaiting Supervisor` (`BR-04`) and makes it visible to the Programme Coordinator (`PC-02`).
* **AC-F20-02 (Positive — Supervisor Topic Approval):** Given a topic proposal assigned to a Supervisor (`BR-05`), When the Supervisor approves the topic, Then the proposal status changes to `Approved`, the topic becomes the official project title, an audit log entry (`F-82`) is written, and the Student receives an in-app and email notification (`F-75`).
* **AC-F20-03 (Validation — Supervisor Rejection Requires Feedback):** Given a Supervisor reviewing an assigned topic proposal, When they attempt to reject the topic without entering feedback, Then the system blocks the rejection and requires supervisory feedback explaining why the proposal was rejected (`PS-03`, `ST-06`).
* **AC-F20-04 (Positive — Student Revision After Rejection):** Given a Student whose topic proposal was `Rejected` with feedback, When the Student submits a revised topic proposal, Then the system links the revised proposal to the rejected proposal, preserves the original proposal in history, sets the new proposal status to `Under Supervisor Review`, and notifies the Supervisor (`PS-05`, `ST-07`).
* **AC-F21-01 (Positive — Individual & Group Allocation):** Given registered students in a Coordinator's Programme and Session, When the Coordinator allocates Student A to an `Individual` project and allocates Students B and C to a `Group` project (`F-22`), Then distinct Project records of type `INDIVIDUAL` and `GROUP` are created and logged in `F-82` (`BR-03`, `BR-06`).
* **AC-F21-02 (Validation — Prevent Double Allocation):** Given Student B is already allocated to Group 1 in `B.Sc. Computer Science` (`2026/2027`), When the Coordinator attempts to allocate Student B to an Individual Project or to Group 2 in the same Programme and Session, Then the system rejects the action with a conflict error (`DAT-01`).
* **AC-F21-03 (Business Rule — Supervisor Assignment Requires Submitted Topic Proposal):** Given a student or group that has not yet submitted a topic proposal (`F-20`), When the Coordinator attempts to assign a Supervisor (`F-24`), Then the system blocks the assignment and informs the Coordinator that a topic proposal must be submitted before Supervisor assignment (`BR-04`, `BR-05`).
* **AC-F22-01 (Positive — Group Creation & Member Visibility):** Given three unallocated registered students in `B.Sc. Computer Science` (`2026/2027`), When the Project Coordinator creates group `CSC-GRP-01` with those three students and designates one as submitter, Then the group is created, all three students can view the complete member list (`ST-17`), and an audit entry is logged (`F-82`) (`BR-07`).
* **AC-F22-02 (Validation — Minimum Group Size):** Given an authenticated Project Coordinator, When they attempt to create a Project Group with only $1$ student selected, Then the system rejects the creation with a validation error requiring at least $2$ students for a group project (`BR-06`).
* **AC-F22-03 (Permission — Student Cannot Modify Group Membership):** Given an authenticated Student assigned to `CSC-GRP-01`, When they view their group workspace, Then they can view group members (`ST-17`) but have no permission or action to add, remove, or transfer group members (`BR-07`, `SEC-11`).
* **AC-F23-01 (Positive — Designated Submitter Formal Submission):** Given Student A is designated as the Group Submitter for `CSC-GRP-01` (`PC-07`), When Student A uploads and submits the Milestone 1 document on behalf of the group (`ST-20`), Then the system accepts the formal submission, records Student A as the submitting representative on behalf of `CSC-GRP-01`, and updates the group's milestone status for all members (`BR-08`, `DAT-04`).
* **AC-F23-02 (Permission — Block Non-Designated Member from Formal Submission):** Given Student B is a member of `CSC-GRP-01` but is *not* designated as a Group Submitter, When Student B attempts to execute a formal milestone or final project submission (`F-32`), Then the system blocks the operation with a `403 Forbidden` error (`BR-08`, `DAT-04`).
* **AC-F23-03 (Validation — Group Must Retain at Least One Submitter):** Given `CSC-GRP-01` has only Student A as Designated Submitter, When the Coordinator attempts to revoke Student A's submitter status without selecting another group member as Designated Submitter, Then the system rejects the update with a validation error (`BR-08`).
* **AC-F24-01 (Positive — Individual & Group Supervisor Assignment):** Given an Individual Project and a Group Project that have both submitted topic proposals (`F-20`), When the Project Coordinator assigns `Available` Supervisor Dr. Okonkwo to both projects, Then Dr. Okonkwo gains supervisory access to both projects (`PC-08`, `PC-09`), the topic proposals transition to `Under Supervisor Review`, notifications are dispatched, and audit records are logged (`F-82`) (`BR-05`, `SEC-12`).
* **AC-F24-02 (Permission — Supervisor Scope Isolation):** Given Dr. Okonkwo is assigned to Project 1 but not Project 2, When Dr. Okonkwo attempts to view or review Project 2, Then the system denies access with `403 Forbidden` (`SEC-12`).

### Module D: Supervisor Capacity and Assignment Management (`F-27`)

* **AC-F27-01 (Positive — Seamless Handover & Continuity):** Given Project X has Milestone 1 approved by Supervisor A and Milestone 2 currently awaiting review, When the Coordinator reassigns Project X to Supervisor B with reason `Supervisor A on sabbatical leave`, Then Supervisor B gains full access to Project X (`PS-20`), Milestone 1 remains `Approved`, Supervisor B can review and approve Milestone 2, and Supervisor A can no longer access or modify Project X (`SEC-12`).
* **AC-F27-02 (Business Rule — Examiner Independence Preserved Across Reassignment):** Given Supervisor A previously supervised Project X before it was reassigned to Supervisor B, When the Coordinator later attempts to appoint Supervisor A as a Project Examiner (`F-46`) for Project X, Then the system blocks the appointment (`BR-16`, `F-48`).

### Module E: Project Workspace and Lifecycle (`F-28`–`F-35`)

* **AC-F28-01 (Positive — Student Workspace & Requirements Access):** Given an authenticated Student registered in `B.Sc. Computer Science` (`2026/2027`), When they open their Project Workspace (`ST-01`), Then they can view the programme's project requirements and guidelines (`ST-02`), their topic status, and their configured milestones and deadlines (`ST-03`) (`SEC-11`).
* **AC-F28-02 (Positive — Supervisor Assigned Projects Dashboard):** Given an authenticated Project Supervisor assigned to $5$ individual projects and $2$ group projects, When they open their Supervision Dashboard (`PS-06`), Then all $7$ assigned projects are displayed with their current milestone stage and pending review indicators, and no unassigned projects are visible (`SEC-12`).
* **AC-F28-03 (Permission — Cross-Student Workspace Isolation):** Given Student A and Student B are on separate individual projects, When Student A attempts to access Student B's Project Workspace URL, Then the system denies access with a `403 Forbidden` response (`SEC-11`).
* **AC-F29-01 (Positive — Sequential Milestone Configuration):** Given an authenticated Project Coordinator, When they configure Milestone 1 (`Chapter 1`), Milestone 2 (`Chapter 2 & 3`), and Milestone 3 (`Final Consolidated Project` of type `FINAL_SUBMISSION`), Then the ordered milestone structure is saved and visible to all Students (`ST-03`) and Supervisors (`PS-07`) in the Programme and Session (`BR-03`).
* **AC-F29-02 (Business Rule — Sequential Progression Gating):** Given a Student whose Topic Proposal is `Approved` and Milestone 1 is currently `Under Review` (not yet `Approved`), When the Student views Milestone 2 or attempts to upload a formal submission to Milestone 2, Then Milestone 2 is displayed as `Locked` and the system rejects any submission to Milestone 2 (`BR-10`).
* **AC-F29-03 (Data Integrity — Prevent Deleting Milestone with Submissions):** Given Milestone 1 already has at least one student submission (`F-32`), When the Coordinator attempts to delete Milestone 1, Then the system blocks the deletion to preserve academic submission history (`DAT-01`, `DAT-02`).
* **AC-F30-01 (Positive — Setting Chronological Deadlines in Institutional Timezone):** Given Milestones 1 and 2 in an institution configured with timezone `Africa/Lagos`, When the Coordinator sets Milestone 1 deadline to `2026-12-01 23:59 WAT` and Milestone 2 deadline to `2027-01-15 23:59 WAT`, Then the deadlines are saved, displayed to Students (`ST-03`) and Supervisors (`PS-07`) in `WAT`, and registered with the reminder/overdue scheduler (`F-79`, `F-80`) (`BR-NEW-01`, `NFR-DOM`).
* **AC-F30-02 (Validation — Out-of-Order Milestone Deadlines):** Given Milestone 1 has a deadline of `2026-12-15 23:59 WAT`, When the Coordinator attempts to set Milestone 2's deadline to an earlier date (`2026-12-01 23:59 WAT`), Then the system rejects the deadline with a chronological sequence validation error (`BR-03`).
* **AC-F31-01 (Positive — Multi-Level Progress Synchronisation):** Given a Group Project where the Designated Submitter uploads Milestone 1 (`F-32`) and the Supervisor subsequently approves Milestone 1 (`F-33`), When any member of the group (`ST-21`), the assigned Supervisor (`PS-08`), or the Programme Coordinator (`PC-15`, `PC-21`) views the progress tracker, Then Milestone 1 is shown as `Approved` and Milestone 2 is shown as `In Progress / Unlocked` across all three actor views (`BR-10`).
* **AC-F31-02 (Positive — Coordinator Bottleneck Filtering):** Given a Programme Coordinator viewing `PC-15`/`PC-21`, When they filter the programme table by `Milestone 2` and status `Revisions Requested`, Then the system displays only the projects in their Programme and Session that are currently in `Revisions Requested` for Milestone 2 (`BR-03`).
* **AC-F32-01 (Positive — Valid Milestone Submission):** Given a Student with an unlocked Milestone 1, When they upload a valid $12\text{ MB}$ `DOCX` file and confirm submission before the deadline, Then the system validates the file content, stores it as `Version 1` (`F-76`, `F-78`), sets status to `Submitted - Awaiting Supervisor Review`, marks it `On Time`, and notifies the assigned Supervisor (`F-75`) (`NFR-SEC`, `DAT-03`).
* **AC-F32-02 (Validation — File Size Over 50 MB & Disguised Extension Rejection):** Given a Student attempting to submit a milestone document, When they select a $55\text{ MB}$ PDF file OR an executable file renamed to `chapter1.pdf`, Then the system rejects the upload with a file-security validation error and does not record a formal submission (`NFR-SEC`, `DAT-03`).
* **AC-F32-03 (Resilience — Interrupted Upload Recovery Without Duplicate Versions):** Given a Student uploading a $30\text{ MB}$ document whose network connection drops at $60\%$, When connectivity is restored and the queued upload automatically retries with the same idempotency token, Then the upload completes and records exactly **one** formal submission version (`NFR-USA`, `DAT-05`).
* **AC-F33-01 (Positive — Milestone Approval Unlocks Next Milestone):** Given Milestone 1 has a submission in `Submitted - Awaiting Supervisor Review`, When the assigned Supervisor reviews and `Approves` the submission (`PS-12`), Then Milestone 1 status becomes `Approved`, Milestone 2 automatically changes from `Locked` to `Unlocked`, an audit record is created (`F-82`), and the Student is notified (`ST-12`, `F-75`) (`BR-09`, `BR-10`, `NFR-AUD`).
* **AC-F33-02 (Positive — Request Revisions Re-opens Resubmission):** Given Milestone 1 is `Submitted - Awaiting Supervisor Review`, When the assigned Supervisor selects `Request Revisions` and enters feedback (`PS-11`), Then Milestone 1 status becomes `Revisions Requested`, Milestone 2 remains `Locked`, the Student can upload `Version 2` (`F-35`), and the Student receives a notification (`F-75`) (`BR-09`).
* **AC-F33-03 (Validation — Feedback Mandatory on Revision Request or Rejection):** Given a Supervisor reviewing a submission, When they attempt to click `Request Revisions` or `Reject` without providing feedback text, Then the system blocks the action and displays a validation error (`BR-09`).
* **AC-F34-01 (Positive — Contextual Feedback & Submission Discussion):** Given a Student has submitted `Version 1` of Milestone 1 (`F-32`), When the assigned Supervisor posts formal feedback (`PS-10`) and the Student replies with a clarifying question on that submission (`ST-22`), Then both the feedback and reply are displayed within the Milestone 1 `Version 1` discussion thread (`ST-13`, `PS-16`, `BR-27`).
* **AC-F34-02 (Scope Boundary — No General Messaging Outside Submissions):** Given an authenticated Student or Supervisor, When they navigate the platform, Then all discussion threads are bound to specific project submissions (`BR-27`) and no standalone general-purpose chat/DM feature exists (`mvp-p.md` §10).
* **AC-F35-01 (Positive — Resubmission Creates New Version & Preserves Previous Version):** Given `Version 1` of Milestone 1 was returned by the Supervisor with `Revisions Requested`, When the Student uploads a revised document with a revision note (`ST-14`), Then the system creates `Version 2`, keeps `Version 1` and its feedback intact (`BR-11`, `DAT-02`), sets Milestone 1 back to `Submitted - Awaiting Supervisor Review`, and notifies the Supervisor (`F-75`).
* **AC-F35-02 (Positive — Version History Inspection & Comparison):** Given Milestone 1 has `Version 1` (`Revisions Requested`) and `Version 2` (`Awaiting Review`), When the Supervisor (`PS-14`, `PS-15`) or Student (`ST-15`) opens the Version History view, Then they can inspect both `Version 1` and `Version 2`, compare `Version 1`'s feedback against `Version 2`'s revision summary, and download either document file (`F-77`).
* **AC-F35-03 (Data Integrity — Historical Versions Cannot Be Deleted):** Given any recorded formal submission version (`v1`, `v2`, etc.), When any user attempts to delete or overwrite a historical version, Then the system blocks the operation (`DAT-02`).

### Module F: Group Collaboration (`F-36`–`F-39`)

* **AC-F36-01 (Positive — Group Member Shared Workspace Access):** Given Students A, B, and C are assigned to Group `CSC-GRP-01`, When any of the three students logs in, Then they can access the `CSC-GRP-01` Shared Group Workspace (`ST-16`) and view the same milestones, shared files, and supervisory feedback (`SEC-11`).
* **AC-F36-02 (Permission — Cross-Group Isolation):** Given Student D belongs to `CSC-GRP-02`, When Student D attempts to access the `CSC-GRP-01` Shared Group Workspace, Then the system denies access with a `403 Forbidden` error (`SEC-11`).
* **AC-F36-03 (Confidentiality — Individual Grade Privacy Within a Group):** Given results are published for `CSC-GRP-01` (`F-60`), When Student A views their results in the workspace, Then Student A sees the shared Examiner assessment and their own individual Supervisor score/final grade, and cannot view Student B's or Student C's individual Supervisor score or final grade (`BR-NEW-02`, `FR-121`).
* **AC-F37-01 (Positive — Non-Submitter Member Uploads & Revises Shared Document):** Given Student B is a non-submitter member of `CSC-GRP-01`, When Student B uploads `draft_chapter2.docx` ($8\text{ MB}$) to Shared Documents (`ST-18`), Then the document is stored and immediately visible and downloadable by all members of `CSC-GRP-01`, without triggering a formal milestone submission (`BR-08`).
* **AC-F37-02 (Positive — Designated Submitter Promotes Shared Document to Formal Submission):** Given `draft_chapter2.docx` (`Revision 3`) is in `CSC-GRP-01` Shared Documents and Milestone 2 is unlocked, When Designated Submitter Student A selects that shared document and confirms a Formal Submission for Milestone 2 (`F-32`, `ST-20`), Then a formal Milestone 2 submission (`Version 1`) is recorded and sent to the Supervisor for review (`BR-08`).
* **AC-F37-03 (Validation — File Security Enforcement on Shared Documents):** Given a group member attempting to upload a `.zip` file or a $60\text{ MB}$ `.pptx` file to Shared Documents, When the upload is initiated, Then the system rejects the file with a format/size validation error (`NFR-SEC`).
